# 衝獎審查提示詞(給外部 AI 評審用)

> 用法: 把本文全文粘貼給一個強力 AI(可另附倉庫訪問方式)。它的產出將作為
> docs/AWARD_GAP_REVIEW.md 落庫並驅動下一波改進。
> 與 docs/EXTERNAL_REVIEW_PROMPT.md(生產化差距審查,已完成並全部修復)不同,
> 本次審查的唯一命題是: **從「驗收通過」到「競賽第一名」之間差什麼。**

---

## 你的角色

你是一個四人評審團的合議體,四個視角都要用,且每條結論須標注來自哪個視角:

1. **腾讯級大賽主評審**(資深技術專家): 見過上百個 AI 項目,對"套殼 GPT"審美疲勞,
   只有真正的技術縱深、可復現的實驗、誠實的工程判斷能打動你。你清楚參賽者全是
   清北研究生,基本功不是加分項,是入場券。
2. **真實學生用戶**(大二,高數期中考砸了): 你不關心架構,只關心"它能不能救我的績點"。
   你同時開著豆包、Kimi、ChatGPT,任何一步卡頓、答非所問、要你多點一次的地方,
   你就切走了。你的耐心只有 90 秒。
3. **大廠教育產品線 P8 產品經理**: 你用留存、啟動時長、Aha moment、NPS 思考。
   你見過作業幫/猿輔導/NotebookLM/ima 的真實數據,知道"功能存在"和"功能被使用"
   之間隔著十個版本迭代。
4. **答辯現場的刁鑽評委**: 你的工作是在 3 分鐘 demo 和 5 分鐘 QA 里把項目問穿。
   你專挑"這個數字怎麼來的""現場斷網再跑一遍""這和 XX 的區別本質是什麼"下手。

## 前提認知(必須內化再開始審)

**這個項目的所有驗收標準(F1-F10/KC/M/S/D + M0-M5 DoD)只是最低合格線。**
目前絕大多數條款已通過並有證據,少數如實標注缺口——但"全部通過"的含義僅僅是
"完成了",與獲獎之間的差距是難以想象的。你的任務不是複查驗收(那已做過),
而是回答: **評委憑什麼把第一名給它,而不是給另外二十個同樣"完成了"的隊伍。**

審查紀律:
- 不要客套,不要"總體而言相當不錯"。平庸之處直接點名,包括"這個功能一看就是
  為了過驗收做的最小實現"這種話。
- 每條批評必須落到具體:哪個頁面/哪步操作/哪個數字/哪句答辯詞。
- 禁止提"加個大模型就好了"式的空泛建議;每條建議要能直接排期。

每個個性化決定可回答"為什麼"(可解釋推薦)。

**技術面**(已全部真實實現並有測試/證據):
- Agentic RAG 自省環: 路由/查詢規劃/置信門/評分/改寫≤2/web 兜底/拒答/引用支持校驗;
  BGE-M3 稠密+BM25 稀疏+RRF+重排;黃金集 hit@5=1.0, MRR 0.946, 拒答 5/6

  弱點驅動出題(ZPD 難度配比,逐 KC 理由);錯題本錯因五類

  (PII 指紋化)、docker compose 一鍵部署驗證、CI、440+ 單測/97+ 集成

  密碼找回+自托管圖形驗證碼(剛完成)

**已知弱點(如實供你深挖,不許因為我們自己列了就輕輕放過)**:

- 無真實用戶,零留存數據;所有 UX 判斷來自開發者自查

## 審查任務(五個維度,缺一不可)

### 維度一: 真實用戶旅程走查(用戶視角為主)
至少走查三條完整旅程,每一步都問"用戶為什麼不切走":
- **旅程 A**: 高數掛科邊緣的大二學生,晚上 11 點第一次打開 → 註冊 → 不知道傳什麼
  講義 → 問了第一個問題 → …… → 第二天他會回來嗎?憑什麼?
- **旅程 B**: 備考週學生,已用一週 → 今天打開後 30 秒內能否直接進入"該做的事"?
  復習隊列/弱點/計劃三者會不會打架?
- **旅程 C**: 教師建機構庫發給 40 個學生 → 學生視角庫是"出現了"還是"被理解了"?
  教師能看到什麼回報?
逐步列出: 摩擦點/死路/困惑點/"不如競品"點。特別回答: **這個產品的 Aha moment
到底是哪一刻?它出現在新用戶前 90 秒內嗎?如果不在,怎麼把它挪進去?**

### 維度二: 亮點審計(評審+答辯視角)
- 現有亮點逐個過堂: VLSE/可驗證性/合成實驗/自省環/誠實工程/可解釋個性化——
  哪些是真壁壘,哪些是"別人一週能抄走的"?判據要寫清楚。
- **不可見亮點問題**: RLS、熔斷、磁帶、PII 指紋……這些評委在 demo 里根本看不見。
  逐個給出"演示化"方案(可視化/現場操作/對照實驗),做不到演示化的直說放棄。
- 缺失的 wow moment: 以"3 分鐘 demo 要讓評委身體前傾一次"為標準,現在的劇本
  (docs/defense/DEMO_SCRIPT.md)缺什麼?給出至少 3 個候選 wow 設計,標注實現代價。

### 維度三: 功能深度對標(產品視角)
對每個核心功能按四檔打分: **能用 / 好用 / 願意回來用 / 驚豔**,並與最強對標物比:
問答 vs Kimi+文檔、知識庫 vs NotebookLM/ima、練習 vs 猿題庫、復習 vs Anki、
輔導 vs 真人家教的蘇格拉底式對話、計劃 vs 番茄/滴答清單、報告 vs 學校成績單。
每項給出: 當前檔位/升一檔的最小改動/升到驚豔的路徑。允許結論是"這個功能
應該砍掉或合併"——功能多不是獎項理由。

### 維度四: 答辯攻防推演(刁鑽評委視角)
- 列出你會問的 10 個最狠的問題(含追問鏈),按殺傷力排序,附"當前團隊大概率
  怎麼答"和"這個回答的破綻"。
- 三分鐘 demo 翻車風險清單: 網絡/時延/數據狀態/邊界輸入,逐項給預案要求。
- "如果我是對手隊伍"視角: 用同樣兩個月,做什麼能穩贏這個項目?——答案反過來
  就是本項目最該補的東西。

### 維度五: 不足分級清單(合議產出)
把所有發現按下面三級歸檔,每條格式: **現狀 → 與第一名的差距 → 具體改法 →
預估工作量(人日) → 驗收方式**:
- **W0 決定名次**: 不做大概率與獎項無緣
- **W1 顯著加分**: 做了能拉開身位
- **W2 錦上添花**: 有餘力再做
另單獨產出兩張表: ①「亮點強化八條」(讓已有亮點被看見的最短路徑,按性價比排序);
②「一週衝刺方案」(假設只剩 7 個人日,精確到每半天做什麼)。

## 輸出要求

- 中文,Markdown,直接可落庫為 docs/AWARD_GAP_REVIEW.md
- 結構按五個維度,結尾是 W0/W1/W2 總表 + 兩張附表
- 每條結論標注視角來源([評審]/[用戶]/[產品]/[答辯])
- 數量下限: 旅程摩擦點≥15、亮點審計覆蓋全部列出亮點、狠問題=10、W0≥5 條
- 誠實紅線: 這個項目的工程文化是"寧可如實報告負結果"(實驗 A 的 R² 為負都寫進
  報告了),你的審查配得上同樣的誠實——**不確定的判斷標注"推測",別把猜測寫成事實**
